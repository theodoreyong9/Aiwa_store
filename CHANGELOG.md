# Changelog

## Unreleased

- Android, the Store's page: a new release that comes in during the first 10 seconds after the Store opened replaces the page at once (it is reloaded), instead of waiting for the app to be closed and opened again, which is why a change to the web app showed on Pages before it showed in the app. The page is the same web app; the phone keeps its own checked copy (so it opens offline), and a release arriving later still waits for the next start. Only compiled by CI, not tried on a phone.
- Store: the **Dictate** tab is gone (dictating is the widget's job). Publishing no longer depends on the widget: **＋** in the Store opens the publish sheet over a pasted HTML file (a file that imports `lib/aiwa.js` is taken for a contract, published through Aiwa); the ranking by what the author has mined is the same as before. Wallet: *Send* can scan the recipient's identity (the *QR* button next to your own identity shows it), where only *Receive* could scan. Web app 49 tests (25 in Chromium); the scan of a real identity code is not tested (the test camera shows another code, which is refused).
- Importing a session by its branch: a branch whose work was already pushed to the default branch had no commit of its own left, so the session's link could not be read and Aiwa asked for it again (the case of a session that pushes straight to `main`). The latest commits of the branch are now read when it has none of its own (a cloud session creates its branch locally, so a branch that exists on GitHub was pushed by it). The refusal also says why a repository is named ("Aiwa cherche la branche dans tes dépôts"). Tried against the real branch `claude/github-repos-audit-scc738` in `YourMinedApp`, which now gives its session. Backend version 26, 111 tests (3 of them against real git repositories).
- The empty folder made the session start empty. Read from the CLI's code: before naming the repository, `claude --cloud` asks git whether the current branch is known on the remote (`git show-ref --verify refs/remotes/origin/<branch>`); the stub had no such ref, so the CLI took the folder for work that exists only on the phone, uploaded it, and the cloud session got an empty folder with no remote and one commit (Claude said so: "le dépôt n'est pas rattaché"). Not the GitHub settings, and not the size of the repository. The stub now has that ref (it only says the branch exists on `origin`; the cloud clones it by name) and nothing of the repository is downloaded. Backend version 25, 108 tests. Not run against a real cloud session; the same CLI also asks claude.ai whether the Claude GitHub App is installed on the repository, and that answer is not visible from here.
- Creating a session in a folder the CLI has never seen: the CLI stops on its "do you trust the files in this folder?" dialog (its footer, "Enter to confirm · Esc to cancel", was what the widget showed) and waits for an Enter that nobody gives. The first widget worked because the user had answered once in its single folder (`~/chat-cloud`); this one made a folder per repository, so each asked again. Every session now starts from `~/chat-cloud` again (kept as it is: only `origin` and the branch are set, nothing is deleted), so an answer already given there still holds, and a new one is given once for every repository. Aiwa does not answer the dialog itself: its footer is recognised as a question (the creation stops after 30 s with the CLI's text instead of waiting 150 s) and the message gives the command to answer it once (`proot-distro login ubuntu -- bash -c 'cd ~/chat-cloud && claude'`). Backend version 24, 107 tests. The cause is deduced from the first widget's comment and from the line the phone showed, not read from the full log; that the old folder is trusted on this phone is not known.
- Widget: the mic button no longer carries a badge (the spinning circle that never stopped, and the green tick). It is the same button whatever happens; what the work is doing is said by the status line. The Actions result is still reachable from the settings picker.
- A session no longer starts from a copy of the repository: the repository is only an address. The backend makes an empty folder whose `origin` is the repository (one empty commit, nothing downloaded) and starts `claude --cloud` there; the cloud session clones the repository itself with Claude's own GitHub access, and Claude is told to attach it with `add_repo` if the folder is still the empty stub. Backend version 22 (the app asks for it), 105 tests.
- `aiwa-android.json` at the root of this repository declares its own Termux line (the one of `bootstrap.sh`): the download button copies it and opens Termux when the repository is `Aiwa_store` in the Android mode, which is how the feature can be tried. Without that file the button only downloaded the APK. Backend 104 tests.
- Creating a cloud session: the widget says what it is doing (the backend's `sending_note`: a step of its own, then the last line the CLI printed), and the creation is no longer cut at a fixed 3 minutes: it is given up when the CLI prints nothing for 150 s, or after 10 minutes. Backend 103 tests.
- Android mode: an app that needs Termux can say so. Claude is asked to write `aiwa-android.json` (`{"termux": "<the line>"}`) at the root of the repository when the app needs it; the backend reads it (a public repository only) and the widget's download button then copies the line to the clipboard, shows it, and opens Termux: the line does everything, the APK's download included, as this project's own does. Nothing is run. Reading the APK's own manifest was left out: it can tell that an app talks to Termux, not what to paste. Backend 101 tests; not tried with a real build.
- In the `store` and `aiwa` modes the code of the app is on GitHub: Claude is asked to put the file in the chosen repository (`aiwa-apps/nom.app.html`, on its branch, and on the base branch with the direct integration), where before it was told to push it nowhere (and, with a repository, that contradicted the Push instruction it also received). The widget's `</>` opens it there once the phone has found it (`github` in `sent_app`; a public repository only) and keeps the received copy as the fallback. The globe of the Store's own repository opens the app instead of a browser (the same page, and the same wallet). Backend 98 tests; not tried with a real cloud session.
- The *Claude* button of the widget is always there. It vanished when the list of sessions was emptied (it only showed once a session existed) and came back only with a first message that went. With no session it now opens Claude's Code tab.
- The two PDFs that were lost when the widget moved into this repository are back in the documents list of the `aiwa` mode: *Value, an ontology of the sustainable residue* (`docs/value-ontology.pdf`) and the 16-slide *AIWA carousel* (`docs/AIWA_carousel_16_pages_square_final.pdf`), copies identical to the ones in `Jobber/docs` and `aiwa_project/docs` (the old repositories are untouched). The old widget listed three documents; this one listed four others and dropped the PDFs.
- Widget, sending: the settings (repository, model, Push, Deploy, session name) and the mic are dimmed and locked while a message is on its way, and a tap says why; the line says how many seconds the send has lasted (the backend gives `sending_since`). The documents button next to the mic is for the `aiwa` mode only (it was on `store` too). Adding a session by its branch keeps the picker open and shows the reason in full when it fails, and when the branch is found but no commit names the session, asks for the session's link next (the branch is kept). A session creation whose CLI stops to ask something (trust this folder?) is reported after 30 s with the question and what to do, not after 180 s; a timeout lists what the CLI did and when. Backend 95 tests. The cause of the "délai dépassé" on a new session is not established: `~/aiwa_cloud_last.log` holds the run.
- What the protocol offered and the Store did not use is wired, as far as it can be. **Link with another phone** (wallet page): the two phones swap two codes (shown and read, as in the click duel), then `aiwa-platform`'s replicator exchanges what each lacks, directly, and each wallet signs a reception for what it received. **Who this phone has seen**: `standing()` / `standings()` in `aiwa-lib` give, for every other identity, its position (the proven lower bound or the weighted median, whichever is higher), what is proven, the vote and its witnesses, whether it signed two histories, and its pace against this wallet (§19.4, read from the wallet's own log, no clock; reported, never applied). Linking two real browser pages found two bugs, fixed: a message over 256 KiB closes a data channel (the replicator now bounds a message at 64 KiB as well as 100 events), and the answering side never saw its channel open. The door sheet (a code to show or read) moved out of the viewer so the wallet page can use it. Not wired: hardware roots (§19.2), since nothing here issues any. Tests: lib 113, platform 88, web 46 (one links two pages in Chromium). Not tried between two real phones.
- Sessions: one made elsewhere is added by the name of its branch (`claude/…`), no longer by its link alone (a link names neither the repository nor the branch, so nothing could be read back from GitHub); the picker has *Vider cette liste…* (two taps), which empties the list Aiwa keeps on the phone and touches nothing in Claude. Backend version 21 (the app asks for it), 94 tests.
- No more free conversation: every new session starts on a repository. The widget's mic opens the repository list while none is chosen (its line says "Choisis un dépôt (⎇) pour commencer"), the list has no "Aucun dépôt" entry, the app refuses to send, and the backend refuses both a session without a repository and an attempt to unchoose it. A session begun earlier without one still takes follow-ups.
- Sending from the widget: opening the app while a message was on its way wiped the widget's "Envoi en cours…" (the app took it for a leftover), so the next send was refused as "already running" and shown as "Dernier envoi échoué". The backend now says whether it is working on a message (`sending` in `/api/status`) and the widget follows it, whatever became of the app that sent; a send refused only because another is running no longer counts as a failure, and the widget says so for 20 seconds ("⏳ Envoi en cours : attends"), not only in a toast; a send is no longer cancelled when the screen that started it goes away; and the start script of Termux waits (3 minutes at most) for a message being sent before it restarts the backend after an update. Read from the code, not seen on a phone; the reason a send finally fails (the "Envoi cloud impossible : …" text) is not known.
- The widget no longer says "Prêt · alertes cloud bloquées" (it showed from the first opening, from an old unconfirmed test, even with no session); the state stays in the health screen (*État d'Aiwa*). The *Ne plus le rappeler* entry and the button on the app's page are gone with it.
- Every diagram of the documents is now also a picture (`docs/img/diagrams/`, 62 PNG files), shown in the document with its Mermaid source folded under it: a viewer that does not draw Mermaid (a phone's file viewer, an editor's preview) showed no diagram at all. `node scripts/render-diagrams.mjs` (`npm run diagrams`) draws what changed and rewrites the documents; `--check` runs in CI and fails when a diagram has no picture or its picture is of an older source.
- What Claude says no longer needs the cloud environment to allow `ntfy.sh`, when the session was started on a repository: if the relay command fails, Claude pushes one line (`aiwa-out/SIGNAL`: `app <name> <time>` with the app, `attend <time>` when it waits for an answer, `check <time>` for the relay test) to its own branch, and the backend reads it from `raw.githubusercontent.com` for 45 minutes after each message (public repositories). The app, the alert and the "alerts blocked" notice are all covered. 13 backend tests for it; not tried with a real cloud session.
- `docs/CONTRACTS.md`: how to write a contract (a vote in 20 lines, three rules, sharing events between phones, what a contract cannot do), with `packages/lib/test/contract-guide.test.mjs` running its snippets (4 tests).
- The wallet warns when what it receives comes from an identity that signed two different histories (a fork): `AIWA.accusations()` (proofs only, read-only, no key needed) and a warning under *Receive*. A rewind is deliberately not an accusation here (a payment that travelled slowly would look like one). 3 lib tests.
- Dictation without the backend: the widget no longer says "Prêt" or promises a start that cannot happen. Without Termux it says "Termux manquant", with Termux but no backend (two starts in vain) "Installation manquante", and a tap copies the install line and opens Termux (or its F-Droid page); the restarts stop while it is missing and the widget recovers by itself when the backend answers. A failed last send shows "Dernier envoi échoué" instead of "Prêt". `BackendHealth.kt` (4 JVM tests).
- The Android app follows the site instead of freezing the page it was built with. `release.json` (every file with its SHA-256, a version and a date) is made by the *Pages* workflow and by the Android build; the app downloads the files, checks each against its hash, keeps all of it or nothing, and serves it from its own storage under the same origin from the next start, if it is newer than the copy inside the APK. No signature and no key: what the site publishes is what the phones run. `apps/web/release.mjs`, `scripts/describe-site.mjs`, `SiteRelease.kt` (14 JVM tests, one against a release written by the Node side) and 5 Node tests that tie the two together.
- Initial import of the protocol (`packages/core`), the distribution layer (`packages/platform`) and the wallet API (`packages/lib`) into one workspace, with their tests (core 410, platform 85, lib 95). One lock file; the packages depend on each other through the workspace, not through pinned commits.
- Plain-words explanation in English and French.
- The creator fee: a deployment may set `rewardParams.creatorFee = { address, rateOfT }`. A fixed part of the T share of every burn then goes to that address in the same transaction; readers count it and refuse a commitment at T > 0 whose burn did not pay it. Core 418 tests, lib 100.
- Yellow paper rewritten as a standalone specification (version 1.0), with the creator fee (§11).
- `registry`: app packages signed by their author (`aiwa-app/1`), validation of submissions by pull request with `assessSubmission` (the burns confirmed by the registry itself, the creator fee included), the existing `score / laps` ranking, the permission ratio, refresh; a workflow that reads the submission as data and writes `store/`. 13 tests.
- `apps/web`: the store (ranked list, search, apps in `<iframe sandbox="allow-scripts">`, offline), the wallet (the burn shows the creator fee before signing, send/receive, recovery), publishing (a signed package with the mining evidence, as a pull request). Tested in Chromium.
- `android`: the dictation widget and its Termux backend, now an optional module; one mode, `store` (Claude writes one self-contained HTML app, which opens in the Store's publish sheet), replaces the two modes tied to other projects; the Store runs in a WebView served from the APK's assets; the module starts only once the widget is added or its screen opened. CI builds the APK. Backend 68 tests.
- `docs/BUSINESS.md`.
- Protocol cleanup, no change to what is signed: one signing module for every signed action (`aiwa-core/src/signing.js`; the messages' bytes are pinned by a test), shared hex/hash/base58 helpers, history-style comments removed; `aiwa-lib`'s 1,581-line wallet split into a thin `AIWA` facade over `ledger`, `mining`, `burns`, `payments`, `channel`, `observer`, `backup` and `evidence`. A test that failed one run in six (a hand-rolled base58 that dropped a leading zero byte) is fixed.
- The wallet starts by itself and the Recovery panel is gone: the first tap creates it, the 12 words are kept in the phone's keystore, its history comes back by itself (Android's backup, archive nodes if the deployment lists any, the registry's public baseline of the author). The registry now publishes `store/baselines/<author>.json`.
- Two kinds of app in the store, both submitted on GitHub: `code` (the package carries the HTML) and `aiwa` (the package carries a pointer to a signed bundle published through Aiwa; the registry and the Store both verify it against the pinned manifest id). The Aiwa SDK is built as one module (`lib/aiwa.js`) for such apps, with an example.
- Publishing from the widget: the Publish tab is replaced by one sheet, opened by the ▦ button, that signs with the wallet and opens the pull request on the author's GitHub account (GitHub's device flow, run by the Android app; the token and the 12 words in the Keystore). A browser hands the signed file over instead.
- `android`: the `aiwa` deploy mode next to `store` (backend 73 tests), the `github-login` and secret commands of the host channel, automatic backup (secrets excluded).
- Apps that use the wallet: an app that declares `<meta name="aiwa-wallet">` gets a banner and a door to the page (who the player is, pay through a channel session key, receive, show or scan a code). The **click duel** (`docs/demo-apps/click-duel.html`): two phones linked by WebRTC through two codes, a price per click, 20 seconds, the one who clicked less pays what they clicked, nothing signed per click. Web tests 37 (20 in Chromium).
- Fix, `aiwa-lib`: the wallet's folded state could be left stale when a read overlapped a mining step or a confirmed burn (the commitment then looked unbacked, the position vanished from the screen and from payments). Reads of the state now go one at a time and a fold overtaken by a reset is done again. A test that interleaves them (it failed three times in four before the fix). lib 100 tests.
- Documentation rewritten around how the system works (README with real screenshots and the install steps, plain-words explanation in English and French, the yellow paper in seven parts); every diagram and every `§` reference is checked in CI (`scripts/check-diagrams.mjs`).
- Workflows: *Pages* and *Devnet check* fail, with the reason and the link, instead of passing without doing anything.
- The Store reads QR codes with the camera: decoded in JavaScript (jsQR, tested in Chromium against a fake camera), and `StoreActivity` grants the camera to the page's own origin, for video only, after Android's permission (compiled in CI, never run on a phone). Web tests 40.
- The widget's logo opens the app (the Store), not the dictation text screen; inside the app a **Dictate** tab opens that screen.
- The README's introduction: a distributed ecosystem (build, submit, store, token, play and pay), not only a store.
- Layout from the bottom of the page: the title and the tabs are a bar at the bottom of the screen, a page's content grows upwards from it, the Store's search field is the lowest thing; the viewer's bar (name, Close) is at the bottom too. The README's screenshots are redrawn.
- The click duel says plainly where Solana comes in: the game never touches it; the wallet checks once that received AIWA comes from a real burn, and with no connection a payment counts once the phone has been online (`receive` now answers `pending`).
